# API Contract (v0.2)

Source of truth for the frontend and backend. Behavior below is based on the
current Pydantic models and routes. Any future section marked **Proposed** will
describe an extension that is not implemented yet. Breaking changes (renaming, removing,
or changing an existing type) are announced to the whole team.

## Conventions

| Topic | Rule |
|---|---|
| JSON keys | `snake_case` everywhere |
| IDs | strings (`"C1"`, `"MON_09"`) |
| Times | `"HH:MM"`, 24 hour |
| Days | `"Mon" "Tue" "Wed" "Thu" "Fri" "Sat"` |
| Base URL | `NEXT_PUBLIC_API_URL` (local: `http://localhost:8000`). All routes start with `/api` |
| Requests | unknown fields are rejected (422) |
| Interactive docs | `GET /docs` (FastAPI) |

### Errors (every failure uses this shape)

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "The request data is not valid.",
             "details": [ { "field": "body.rooms.0.capacity", "message": "Input should be greater than or equal to 1" } ] } }
```

Current backend codes: `BAD_REQUEST` (400), `NOT_FOUND` (404),
`METHOD_NOT_ALLOWED` (405), `CONFLICT` (409), `PAYLOAD_TOO_LARGE` (413),
`VALIDATION_ERROR` (422), `NOT_IMPLEMENTED` (501), `INTERNAL_ERROR` (500),
`SOLVER_TIMEOUT` (504), and `HTTP_ERROR` for otherwise unmapped HTTP errors.
AI endpoint errors are listed below.

## Data shapes

```
Faculty        { id, name, preferred_slot_ids: [slot_id] }
Room           { id, name, capacity: int >= 1 }
TimeSlot       { id, day, start, end, label }
Course         { id, code, name, faculty_id, student_count: int >= 0,
                 sessions_per_week: int >= 1, session_length_slots: int >= 1 (default 1) }
ProjectData    { courses: [Course], faculty: [Faculty], rooms: [Room], slots: [TimeSlot] }
Preference     { id, type: "faculty_prefers_slots", faculty_id, slot_ids: [slot_id] }
Constraints    { no_teacher_clash: bool, no_room_clash: bool, room_capacity: bool,
                 preferences: [Preference] }          (all three bools default true)
TimetableEntry { id, course_id, faculty_id, room_id, start_slot_id,
                 length_slots: int >= 1, slot_ids: [slot_id] }
Conflict       { type, message, suggested_fix: string|null,
                 affected_entry_ids: [id], affected_slot_ids: [slot_id] }
GenerateResult { status, timetable: [TimetableEntry], unmet_constraints: [Conflict],
                 preferences_met: int, preferences_total: int }
Project        { id, name, data: ProjectData, constraints: Constraints,
                 timetable: [TimetableEntry] }
```

### AI interpretation schemas

```text
AIClarificationAnswer  { question_id: string, question: string, answer: string }
AIClarificationQuestion { question_id: string,
                          reason: "ambiguous" | "unsupported" | "contradictory",
                          question: string }
AIInterpretRequest    { instruction: non-empty string (max 4000 characters),
                        clarification_answers: [AIClarificationAnswer] (default []) }
AIInterpretReady      { status: "ready", proposed_constraints: Constraints,
                        summary: string, clarification_questions: [] }
AIInterpretNeedsClarification {
                        status: "needs_clarification",
                        proposed_constraints: null,
                        summary: null,
                        clarification_questions: [AIClarificationQuestion] }
AIInterpretResult = AIInterpretReady | AIInterpretNeedsClarification
```

Each clarification answer must have a non-empty question and answer, each no
longer than 1000 characters. The request may include at most 10 answers. Unknown
fields are rejected. Question IDs are UUID strings generated by the backend and
remain unchanged when included in later clarification history. Each answer must
reference a question ID; duplicate IDs in one request are rejected. Because the
endpoint is stateless, IDs correlate client-retained history and are not
authorization tokens or proof that the server retained an earlier response.

### Multi-slot classes

Two slots are *consecutive* only if they are on the same day and the first slot's
`end` equals the next slot's `start` (so a lunch gap blocks a 2-slot lab).
`TimetableEntry.length_slots` is the class length, and `slot_ids` lists **every**
slot it occupies in order, starting with `start_slot_id`. The frontend draws one tall
block from `slot_ids`; it never works out spans itself. When sending edits, `slot_ids`
may be omitted: the backend recomputes it.

### Preferences

`Faculty.preferred_slot_ids` and `Constraints.preferences` both express "prefers
these slots". The solver uses the **union**. `preferences_total` counts one per
preference entry plus one per faculty with a non-empty `preferred_slot_ids`; a
preference is "met" when every session of that faculty's courses lands in a preferred slot.
(Exact counting is finalised in Phase 3. The shape will not change.)

**Current limitation:** `Constraints` supports only the preference type
`faculty_prefers_slots`. It cannot represent course-specific session counts,
priority weights, general preferences that are not tied to faculty, or hard
time exclusions such as "no classes after 16:00".

**AI behavior:** An instruction to add a soft preference may only
become `faculty_prefers_slots` when that is what the user actually requested and
the faculty and slots can be identified. A hard restriction must never be
silently converted into a soft preference. Unsupported requests, ambiguous
references, or contradictions produce clarification questions and no proposed
constraints.

The ready response contains a complete `Constraints` object based on the
project's current constraints. Existing values are preserved unless the user
clearly requests a change expressible by this schema. Hard-rule booleans may
change only when the instruction explicitly requests that change; preferences
must not be used as substitutes for hard rules. Preference IDs are assigned by
the backend, not by Gemini.

### Enums

- `status`: `"complete"` | `"complete_with_unmet_preferences"` | `"impossible"`
- `Conflict.type`:
  - edit clashes (from validate): `teacher_clash`, `room_clash`, `room_capacity`, `missing_reference`
  - solver conflicts (from generate): `no_room_big_enough`, `teacher_overloaded`,
    `not_enough_slots`, `no_consecutive_block`, `blocking_rules`, `preference_unmet`

## Endpoints

| Method | Path | Query | Body | Returns |
|---|---|---|---|---|
| GET | `/api/health` | none | none | `{ "status": "ok" }` |
| POST | `/api/projects` | none | `{ "name": string }` | `Project` (201) |
| GET | `/api/projects/{id}` | none | none | `Project` |
| PUT | `/api/projects/{id}/data` | none | `ProjectData` | `Project` |
| PUT | `/api/projects/{id}/constraints` | none | `Constraints` | `Project` |
| POST | `/api/projects/{id}/generate` | optional `scenario` (mock mode) | none | `GenerateResult` |
| POST | `/api/projects/{id}/validate` | optional `scenario` (mock mode) | `{ "timetable": [TimetableEntry] }` | `{ "valid": bool, "clashes": [Conflict] }` |
| PUT | `/api/projects/{id}/timetable` | none | `{ "timetable": [TimetableEntry] }` | `Project` |
| GET | `/api/projects/{id}/export/pdf` | none | none | PDF file download |
| GET | `/api/projects/{id}/export/ics` | `term_start`, `term_end`, `timezone` | none | ICS file download |
| POST | `/api/projects/{id}/import` | none | CSV files (stretch) | `Project` |
| POST | `/api/projects/{id}/ai-constraints/interpret` | none | `AIInterpretRequest` | `AIInterpretResult` |

For ICS export, `term_start` and `term_end` use `YYYY-MM-DD`; `timezone` is an
IANA timezone name such as `Asia/Kolkata`. `term_start` must be on or before
`term_end`, and the date range cannot exceed 367 calendar days. Generate and
validate accept the optional `scenario` query parameter to select fixtures in
mock mode; it is ignored when `MOCK` is not enabled.

Notes:
- `generate` returns **200** with a `GenerateResult`, including when the
  status is `"impossible"` (a normal result, not an error). When impossible,
  `timetable` is `[]` and `unmet_constraints` explains why. A solver timeout
  returns `SOLVER_TIMEOUT` (504).
- `validate` does not save anything. It checks the timetable against the project's
  current data and constraints using the same rules the solver uses.
- All routes above are implemented in the current backend tree.

### Constraint reference validation

`PUT /api/projects/{id}/constraints` validates every preference `faculty_id`
against the project's faculty IDs and every `slot_id` against its slot IDs.
Invalid references return `VALIDATION_ERROR` (422) in the standard error
envelope. Validation runs inside the storage transaction, so failed updates do
not change the stored constraints. The same validation applies to user-edited AI
proposals submitted to this endpoint.

### AI interpretation and confirmation workflow

`POST /api/projects/{id}/ai-constraints/interpret` loads the project by `{id}`.
Its request contains the original instruction and the complete list of
question/answer pairs from prior clarification rounds; the client resends the
same original instruction on every round. Each answer references the stable
`question_id` from a previous response and includes that question's text so the
API can reconstruct the clarification context. The API is stateless and does
not persist the instruction or clarification history. Starting a different
instruction starts a new clarification sequence with an empty answer list.

The API sends Gemini only the instruction, clarification history, current
constraints, and the minimum project course, faculty, and slot information
needed to resolve user references. The endpoint only interprets. It does not
save constraints, edit project data, call the solver, or return timetable
entries. The API validates the provider output with Pydantic and checks
referenced faculty and slot IDs against the loaded project before returning
`ready`. The official Google GenAI SDK requests structured JSON output, and the
response is validated with the Pydantic schemas used by the API.

If the instruction is ambiguous, contradictory, or unsupported, the response
has `status: "needs_clarification"`, `proposed_constraints: null`, and one or
more questions. It never returns partial constraints alongside unresolved
requirements. In particular, hard restrictions must not be converted into soft
preferences. A request to change course session counts or any other project
data is outside this endpoint's scope and requires clarification or a separate
user edit through the data endpoint.

When all requirements are supported and clear, the response has
`status: "ready"` with a complete `proposed_constraints` object. This object
preserves all existing settings unless the user explicitly requests a
supported change. The user reviews or edits it and explicitly confirms. Only
then does the client send it to `PUT /api/projects/{id}/constraints`. After
that succeeds, the client may call the existing
`POST /api/projects/{id}/generate`; the existing OR-Tools solver remains the
only source of timetable output.

AI endpoint errors use the common error envelope:
- `NOT_FOUND` (404): project does not exist.
- `VALIDATION_ERROR` (422): request fields are invalid.
- `AI_NOT_CONFIGURED` (503): `GEMINI_API_KEY` is missing.
- `AI_RATE_LIMITED` (429): Gemini rate limit reached.
- `AI_PROVIDER_ERROR` (502): another Gemini provider failure.
- `AI_RESPONSE_INVALID` (502): provider response is malformed or invalid
  against the Pydantic response schema.
- `AI_TIMEOUT` (504): Gemini did not respond before the configured timeout.

### Gemini server configuration

The backend reads `GEMINI_API_KEY` and `GEMINI_MODEL` from its server-side
environment. The default model ID is `gemini-3.1-flash-lite`; it is a
stable model ID listed in Google's current Gemini API model documentation and
is currently listed with free-tier input and output pricing. Account-specific
model access and quotas cannot be confirmed from this repository and must be
checked for the configured Google AI Studio project. The model remains
configurable with `GEMINI_MODEL`. The API key must never be sent to or exposed
in the frontend.

## Mock mode (for frontend development)

With `MOCK=1` the backend returns canned generate and validate responses from
`backend/fixtures/`; the sample project fixtures seed demo projects. AI
interpretation always uses the configured Gemini provider and requires
`GEMINI_API_KEY`, including when mock mode is enabled.
